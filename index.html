🔍 Root Cause: Incorrect Loss Masking The training loop used manual pre-tokenization (Cell 8) before passing data to the trainer. This bypassed Unsloth's completion-only masking entirely, setting labels = input_ids for the full sequence. The ~3,460-token system prompt dominated the gradient signal — the actual function call answer (~50 tokens) contributed only ~1.4% of the loss. The model learned to reproduce the prompt structure, not to call functions.

3 The Enum Problem — Deep Dive

14 tools had enum constraints. Most were broken. Here's how we fixed them.

🔍 Enum Audit Results

14 out of 36 tools have enum-constrained parameters. During the initial audit we discovered three severity levels:

💀 6 Completely Dead Tools All training rows had None in their optional enum fields. The dataset generator incorrectly flagged None as a violation, so every single row for these tools was excluded from training. The model had zero examples to learn from for these functions.

Examples: search_flights, set_reminder, get_prayer_times, calculate_loan, calculate_math, track_shipment
⚠️ 6 Partially Damaged Tools Mix of None values (incorrectly excluded) plus some rows with genuine Arabic or variant-English enum values that didn't match the expected canonical English enum. Both issues combined to reduce training coverage significantly.

Examples: book_government_appointment, calculate_end_of_service, and others with Arabic-language ground truth values like "استقالة" instead of "resignation".
✅ 2 Mostly Fine Tools calculate_end_of_service: 86% valid rows — minor Arabic/variant mapping needed.

get_directions: only 1 affected row — essentially fine.

These required minimal intervention.

🛠️ Two-Phase Fix Strategy

Phase 1 (v3): Enum Value Normalization Wrote normalize_enum_values.py — a script that scans every tool schema for enum-constrained parameters and maps non-compliant ground-truth values (Arabic, variant English, free-text) to their canonical enum values. For example, "استقالة" → "resignation", "فصل" → "termination", "تجديد جواز" → "passport". This brought enum_compliance from 0% to 100%. However, FuncName dropped slightly because the "None = violation" bug still excluded the 6 dead tools.
Phase 2 (v4): Allow None for Optional Enum Fields Added a recheck_pass_enum_none_allowed() function that re-evaluates every row using corrected logic: None in an optional enum field is now valid. This recovered all 6 completely dead tools and fixed the partially damaged ones. Thousands of previously excluded rows re-entered the training set, resulting in massive domain-level improvements (islamic_services +23%, banking_finance from 0 to 35%).
# Phase 1 — normalize Arabic / variant values to canonical enum strings ENUM_MAPPINGS = { "calculate_end_of_service": { "termination_type": { "استقالة": "resignation", # Arabic → English "فصل": "termination", "Resigned": "resignation", # variant English → canonical ... } }, ... } # Phase 2 — re-evaluate with corrected None-is-valid logic def check_enum_compliance(tool, args, enum_fields): for param, allowed_values in enum_fields[tool].items(): val = args.get(param) if val is None: continue # ← key fix: None = valid (user didn't specify) if val not in allowed_values: return False return True
